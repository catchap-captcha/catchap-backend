# 문항 형식이 두 종류인 이유 — 그리고 왜 그대로 두는가

> "왜 전체학습 문항과 강의 캡차 문항의 형식이 다르지?"에 대한 답.
> 결론: **다른 게 맞다. 목적이 다르기 때문이다.** 억지로 통일하면 오히려 나빠진다.
> 관련 코드: `app/services/subject_banks.py`, `app/services/captcha_service.py`
> (`_wrap_bank_question`), `app/api/v1/endpoints/captcha_api.py`(`_lecture_challenge`).

---

## 1. 두 형식

**전체학습 문제은행** (`questions` 테이블, `korean_bank.py` 등)
```jsonc
{ "type": "single" | "multi" | "drag" | "connect" | "sort" | "order" | ...,  // 30여 종
  "options": [{"id": "o1", "emoji": "😊", "text": "기쁘다"}, ...],  // 리치 객체
  "answer": "o3" }                                                  // 정답 = 옵션 id
```

**강의 캡차 문항** (`lecture_questions` 테이블, LLM 생성)
```jsonc
{ "options": ["가", "나", "다"],   // 문자열 배열
  "answer_index": 2 }              // 정답 = 위치 번호
```

---

## 2. 왜 다른가 — 출신과 목적이 다르다

| | 전체학습 은행 | 강의 캡차 |
|---|---|---|
| 언제 생겼나 | 아동 캡차 시절(원본 catchap-service JSON 이식) | 인강 전환 후(LLM 생성) |
| **내용 형식** | 드래그·연결·순서·그리기 등 **조작형 30여 종** | **4지선다 텍스트 하나** |
| **화면 상호작용** | 유형별(드래그·연결·순서…) | **드래그(끌어 담기)** ← 4지선다지만 클릭 아님 |
| 목적 | 학습 + **행동 데이터 수집** | 시청 검증 + **행동 데이터 수집** |
| 정답 표기 | 옵션 id (위치 무관 — 셔플·조작형 지원) | 위치 번호(내용 단순) |

> **중요 — "강의 캡차 = 4지선다"는 절반만 맞다.** 강의 캡차의 *내용 형식*은 4지선다가
> 맞지만(LLM 생성이 쉽고 시청 검증엔 충분), *화면 상호작용*은 클릭이 아니라
> **드래그(끌어 담기)**다. `_lecture_challenge`가 단일 정답 문항도 `type:"multi"`로
> 내려 위젯이 "정답을 상자로 끌어다 놓기"로 그린다. 이유는 §3과 같다 — 클릭 한 점은
> 행동 신호가 없지만 드래그는 궤적을 남긴다. 즉 강의 캡차는 **"4지선다 내용 + 드래그
> 상호작용"**으로 두 목적(생성 단순 + 행동 데이터)을 이미 함께 취하고 있다.

- 은행이 **id 기반**인 이유: 드래그·연결에는 "몇 번째 보기"라는 개념이 없다. 보기를
  화면에서 섞어 뿌려도 정답을 추적하려면 위치가 아니라 안정적인 id가 필요하다.
- 강의 문항이 **index 기반**인 이유: LLM이 자막에서 뽑는 건 4지선다 텍스트뿐이다.
  LLM에게 "옵션마다 o1/o2 id를 붙이고 정답을 id로 내라"고 시키면 불필요하게 복잡하고,
  LLM이 id를 헷갈려 잘못 내는(환각) 위험만 커진다. 가장 단순한 형식이 맞다.

---

## 3. ★핵심: 행동 데이터 관점에서 전체학습은 '조작형(드래그)'이 우월하다

전체학습의 목적 하나는 **행동 데이터 축적**이다(마우스 궤적·속도·주저·드롭 정확도 →
봇/사람 판별, `behavior_traces` 테이블). 이 관점에서 문항 유형의 가치가 갈린다:

- **4지선다 클릭은 신호가 거의 없다.** 남는 건 "어느 보기를 눌렀나 + 언제"뿐.
  봇이든 사람이든 클릭 한 번은 똑같아 보인다.
- **드래그는 연속 궤적을 남긴다.** 집는 순간부터 놓는 순간까지의 경로·가속·미세
  떨림이 전부 기록된다. 사람 손은 곡선·불균일 속도, 자동화는 직선·등속이거나
  부자연스럽게 정확하다 — **그 차이가 드러나는 캔버스**가 드래그다.

→ **결론: 전체학습 은행의 조작형(드래그 등) 형식은 버릴 부채가 아니라 자산이다.**
  전체학습을 "단순 4지선다로 통일"하는 방향은 데이터 파이프라인의 가장 좋은
  입력을 스스로 끊는 것이라 **하지 않는다.** (이 판단은 사용자 결정 2026-07-18.)

### 3.1 그래서 형식을 통일하지 않는다

- 전체학습 은행: 조작형 리치 형식을 **유지·강화**한다.
- 강의 캡차: *내용*은 4지선다(생성 단순·검증 충분)로 두되, *상호작용*은 이미
  드래그(끌어 담기)라 행동 데이터도 얻는다 — 위 표의 주석 참고. "단순 4지선다"가
  아니라 "4지선다 내용 + 드래그"다.
- 둘 사이는 **변환 계층**(`to-bank` 엔드포인트, `lecture-question-pipeline.md` §6)이
  다리를 놓는다. 서로 다른 두 시스템을 무리하게 합치는 것보다, 경계에서 변환하는
  것이 안전하다(실무의 일반 원칙: *anti-corruption layer*).
- 참고: 강의 캡차가 이미 4지선다를 드래그로 렌더하므로, "LLM 4지선다를 은행에 넣을 때
  드래그로 승격"은 새 위젯이 아니라 같은 `multi` 렌더러를 은행 배치 경로에도 적용하는
  문제로 좁혀진다(향후 검토).

## 4. 보기 순서는 발급마다 섞는다 (셔플 정책)

`_wrap_bank_question`은 선택형 보기(`options`)를 발급 때마다 `random.sample`로 섞는다.

**왜:**
1. **정답 위치 암기 차단** — 순서가 고정이면 "매번 3번"처럼 내용 없이 통과한다.
   (자기검증 solver의 셔플과 같은 이유 — `lecture-question-pipeline.md` §3.2 A.)
2. **행동 데이터 편향 제거** — 보기 위치가 고정이면 궤적이 늘 같은 좌표로 쏠려
   봇/사람 판별 신호가 편향된다. 섞으면 "어느 위치의 정답이든 자연스럽게 찾아가는가"를
   관측할 수 있다.

**왜 안전한가:** answer가 옵션 id(`"o3"`)라, 순서를 바꿔도 채점은 위치가 아니라 id로
비교한다. 순서 자체가 정답인 유형(`order`/`sequence`)은 `options` 필드를 안 쓰므로
영향이 없다.

> 발견 이력: 이 셔플은 2026-07-18에야 실제로 켜졌다. 그 전까지 은행 single/multi는
> 보기 순서가 고정(o1,o2,o3,o4)이었다 — id 기반이라 셔플이 **안전한데도** 안 하고
> 있었다. "왜 형식이 다른가" 질문을 파다가 드러났다. (교훈: 안전한 개선이 그냥
> 방치돼 있을 수 있다. 데이터 목적을 기준으로 기존 동작을 다시 의심할 것.)

### 4.1 남은 개선 (알려진 것)

- **강의 캡차 보기 셔플은 아직 없다.** `_lecture_challenge`는 `answer_index` 기반이라
  섞으려면 id 재매핑이 필요하다(은행처럼 안전하지 않다). 강의 캡차는 같은 시점의
  여러 문항 중 무작위로 하나를 뽑으므로 위치 암기 위험이 은행보다 낮지만, 같은
  문항이 재출제되면 위치가 고정이다 — 개선 여지로 남긴다.
