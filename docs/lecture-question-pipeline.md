# 강의 확인 문항 자동 생성·자기검증 파이프라인

> 이 문서는 "왜 이렇게 만들었는지"를 팀이 공부할 수 있게 남기는 설계 노트입니다.
> 코드만 보면 "무엇을" 하는지는 알아도 "왜"는 안 보이기 때문입니다.
> 관련 코드: `app/clients/ai_client.py`, `app/clients/stt_client.py`,
> `app/api/v1/endpoints/lectures.py`(`ops_generate_questions`).

---

## 0. 한 줄 요약

강사가 올린 강의 영상에서 **AI가 "시청 확인 문제"를 자동 생성**하고, **그 문제가
'강의를 봐야만 풀리는 문제'인지 AI로 되검증**해서, 강의 중 캡차(시청 검증)에 쓸지
전체학습 문제은행에 쓸지 강사가 판단하도록 돕는다.

핵심 아이디어 한 문장: **"강의를 안 본 AI(=봇)가 풀 수 있는 문제는 시청 검증용으로
쓸모가 없다."** 그래서 그런 문제를 걸러낸다.

---

## 1. 우리가 푸는 문제 (배경)

CatChap의 강의 캡차는 "이 학생이 영상을 실제로 봤는가"를 검증한다. 검증 수단은
영상 중간중간(체크포인트)에서 내용 확인 문제를 내고 못 맞히면 되감아 다시 보게
하는 것이다.

그런데 확인 문제가 **강의를 안 봐도 상식으로 풀리면** 검증이 무의미하다.
예: 강의 주제가 "덧셈"인데 문제가 "1+1은?"이면 영상을 안 본 사람도, **봇(자동화
프로그램)도** 그냥 통과한다. 캡차의 존재 이유가 사라진다.

즉 좋은 시청 확인 문제의 조건은 **"그 강의를 실제로 본 사람만 풀 수 있어야 한다"**.
이걸 사람이 문항마다 일일이 판단하면 느리고 일관성이 없다. → **AI로 판정하자.**

## 2. 전체 파이프라인 (누가 무엇을 하는가)

```
[강사가 강의 영상 업로드]
        │
        ▼
① STT (음성 → 자막)                     ← app/clients/stt_client.py
   OpenAI Whisper. 영상의 말소리를
   [12초~15초] "오늘은 분수를..." 형태의
   타임스탬프 붙은 자막으로.
        │
        ▼
② 생성 LLM (자막 → 확인 문제)            ← ai_client.generate_lecture_questions
   Anthropic Claude. 자막을 근거로
   4지선다 문제 + 출제 시점(position) +
   되감기 지점(content_start)을 만든다.
        │
        ▼
③ 검증 LLM (문제 → 봇 저항성 판정)        ← ai_client.verify_questions   ★이 문서의 핵심
   "강의를 안 본 AI"가 이 문제를 풀어본다.
   풀리면 = 상식 문제, 안 풀리면 = 강의 필요.
        │
        ▼
④ 강사 검수 (배지 보고 최종 결정)         ← 프론트 OpsLectures 화면
   AI 판정은 '참고 신호'. 강사가 배지를
   보고 캡차로 쓸지/은행으로 보낼지/버릴지 결정.
        │
        ├─ 강의 캡차로 (draft → active)   → 시청 검증에 사용
        ├─ 전체학습 은행으로              → 지식 문제로 사용 (※ 자동삽입 미구현, §6)
        └─ 폐기                           → 불량 문항 제거
```

**왜 LLM을 2개 쓰나?** ②는 "문제를 만드는 역할", ③은 "그 문제를 공격자 입장에서
풀어보는 역할"이다. 만드는 쪽과 검증하는 쪽을 분리하는 것이 이 설계의 뼈대다.
(STT는 LLM이 아니라 음성인식이므로, 'LLM 2개 + STT 1개'가 정확한 표현이다.)

## 3. 왜 이 기술을 골랐나 (③ 검증 LLM의 설계 근거)

### 3.1 기법 이름: Adversarial Filtering (적대적 필터링)

머신러닝 데이터셋을 만들 때 쓰는 표준 기법이다. "모델이 **지문(맥락) 없이** 풀 수
있는 문항은 그 데이터셋의 목적에 맞지 않으니 제거한다"는 발상. 유명한 독해
데이터셋들(예: 지문 없이도 정답이 찍히는 문항 골라내기)이 이 방식으로 품질을
높였다. 우리는 "지문" 자리에 "강의 영상(자막)"을 넣은 것이다.

→ 팀원이 더 공부하려면 키워드: *adversarial filtering*, *answer-only baseline*,
  *annotation artifacts*.

### 3.2 세 가지 보강 — "왜 단순히 한 번 풀리는지만 보지 않았나"

순진하게 "검증 LLM이 한 번 풀면 상식 문제"로 판정하면 세 가지가 샌다.
각각을 왜 넣었는지가 이 파이프라인 품질의 핵심이다.

**(A) 보기 셔플 + 3회 다수결** — `verify_questions`의 `trials=3`, `_shuffled_variants`

- *문제*: 4지선다는 **찍어도 25%** 맞는다. 좋은 문제 4개 중 1개가 우연히
  "상식으로 풀림"으로 잘못 분류된다.
- *더 나쁜 문제*: 생성 LLM은 정답을 특정 위치(예: 항상 2번)나 가장 긴 보기에
  두는 **버릇**이 있다. 검증 LLM이 지식이 아니라 그 버릇을 눈치채고 맞혀버리면,
  "봇이 풀었다"가 거짓 신호가 된다. (생성·검증이 같은 모델이면 특히 위험 —
  같은 버릇을 공유한다.)
- *해결*: 매 시도 **보기 순서를 무작위로 섞고**(정답 위치 단서 제거) **3번 풀려
  다수결**(우연 정답 완화). `answer_index`도 섞인 순서에 맞게 재계산한다.

**(B) 공개 맥락 제공** — `verify_questions(context=...)`

- *문제*: 실제 공격자는 강의 화면에서 **제목·과목·설명을 본다**. 검증 LLM에게
  문제·보기만 주면, 공격자보다 **불리한 조건**에서 풀게 되어 판정이 후해진다
  ("어? 이거 자막 없으면 어렵네 → 캡차 적합" 오판).
- *해결*: 검증 LLM에게도 공격자가 보는 공개 정보(제목·과목·설명)를 준다.
  판정 조건을 실제 위협 모델과 일치시킨다.

**(C) 자막-포함 풀이로 '불량 문항' 분리** — `verify_questions(transcript=...)`

- *문제*: 검증 LLM이 문제를 "못 푸는" 이유는 둘이다.
  ㄱ. 강의를 봐야 아는 문제 (우리가 원하는 것)
  ㄴ. **문제 자체가 깨진 것** — 생성 LLM이 환각으로 만든 모호한 문제, 정답이
     틀린 문제. 이게 캡차로 나가면 **정직한 시청자도 못 풀어서** 무한 되감기
     지옥에 빠진다. 제품 신뢰를 직접 깎는다.
- *해결*: **자막을 준 상태**로 한 번 더 풀린다. 자막을 줘도 못 풀면 = 사람이
  봐도 근거가 없는 문항 = **불량 의심(discard)**. 이렇게 3분류가 된다:

| 블라인드(자막X) | 자막O | 판정 | 의미 | 배치 |
|---|---|---|---|---|
| 풀림 | — | **bank** | 상식으로 풀림 | 전체학습 은행 후보(캡차엔 부적합) |
| 못 풂 | 풀림 | **captcha** | 강의 의존적 + 근거 있음 | 강의 캡차에 이상적 |
| 못 풂 | 못 풂 | **discard** | 자막을 줘도 안 풀림 | 불량 의심, 폐기 검토 |
| 못 풂 | (자막 없음) | captcha | 불량 판별 불가 | 종전과 동일(한계, §5) |

## 4. 정직성 원칙 (이 코드베이스의 규칙)

CatChap 백엔드는 **"가짜 성공 금지"**를 지킨다. 이 파이프라인에서 구체적으로:

- LLM 키가 없으면 문제를 **지어내지 않고** 503으로 거절한다(stub 생성 금지).
- STT 키가 설정됐는데 전사에 실패하면 **조용히 메타 기반으로 강등하지 않고**
  502로 원인을 노출한다(키 오류·용량 초과를 운영자가 알아야 고친다).
- 검증 LLM이 실패해도 **생성 자체는 살리되**, 조용히 삼키지 않고 응답의
  `verify_error`로 노출한다. 판정 못 한 문항은 `None`(미판정)으로 남긴다.
- 검증 응답 파싱이 애매하면 **보수적으로** 처리한다(답을 못 얻은 문항은
  "못 풀었다"로 = 캡차 후보로 남겨, 상식 문제를 캡차에 잘못 넣는 것보다
  좋은 문제를 은행에 못 보내는 쪽으로 실수한다).

→ 왜? 학습 서비스에서 "성공한 척"이 제일 위험하다. 틀린 판정이 조용히 지나가면
  아이가 못 푸는 문제로 막히거나, 봇이 캡차를 뚫는다.

## 5. 한계 (반드시 알고 써야 하는 것)

1. **우연 정답은 완전히 못 막는다.** 셔플 3회 다수결로 줄였을 뿐. 판정은
   **강사 검수의 참고 신호**지 자동 배치가 아니다. 최종 결정은 사람이 한다.
2. **작정한 공격자는 이긴다.** 봇이 영상 스트림을 자기 STT에 넣고 LLM에 풀리면
   **어떤 텍스트 문항도** 뚫린다. 이 파이프라인은 "봇 차단 보장"이 아니라
   **공짜 우회(맥락 없는 LLM 복붙)를 막아 공격 비용을 올리는 것**이다.
   진짜 방어는 조합이다: 건너뛰기 차단(체크포인트까지 실제 스트리밍 강제) +
   행동 신호 수집 + 드래그 위젯 + (예정) 캡차 응답 시간 상한.
3. **실 LLM 키 없이는 라이브 검증을 못 한다.** 현재 테스트는 LLM 호출을
   모킹한다. 키를 콘솔 설정에 넣으면 그때 실제로 돈다.

## 6. 앞으로 할 일 (방향과 이유)

> 팀원이 "다음에 뭘, 왜 해야 하는지" 알 수 있게 남긴다.

- **[예정] 은행 자동 삽입** — 지금은 "은행 적합" 판정만 하고 실제로 전체학습
  은행(`questions` 테이블)에 넣는 건 강사 수동이다. 자동화하려면 **형식 변환**이
  필요하다: 강의 문항은 `options=["가","나"]`·`answer_index=0` 형식인데, 은행
  문항은 `options=[{id,emoji,text}]`·`answer="o1"`·`type="single"` 형식이다
  (예: `app/services/korean_bank.py`). 변환을 잘못하면 학생 화면에서 문항이
  깨지므로, 착수 시 **은행 payload 스키마부터 대조**할 것.
- **[예정] 캡차 응답 시간 상한** — 봇이 STT→LLM으로 푸는 데는 수십 초 걸린다.
  캡차 문항에 응답 제한시간을 두면 이 우회를 시간으로 압박할 수 있다. 임계값은
  "정직한 학생이 읽고 답하는 시간"을 침해하면 안 되므로 실측 후 결정.
- **[검토] 검증 강화** — 우연 정답을 더 줄이려면 시도 횟수를 늘리거나(비용↑),
  검증 모델을 생성 모델과 **다른 모델**로 두는 방법이 있다(같은 버릇 공유 방지).
- **[규모 시] 비동기 전환** — 지금은 STT 1회 + LLM 여러 회(생성 1 + 검증 4)를
  **한 HTTP 요청에서 동기로** 돌린다. 강사가 소수인 지금은 괜찮지만, 긴 강의·
  다수 강사가 되면 요청 타임아웃·워커 점유가 생긴다. 잡 큐 + 폴링으로 바꿔야
  하는 **알려진 부채**다.
- **[미구현] 중복 생성 방지** — 강사가 생성 버튼을 두 번 누르면 draft가 중복
  생성될 수 있다.
