## 0. 핵심 원리 한 줄

**창고는 커도, 학생의 오늘 큐는 작다.** 문항마다 학생별 상태를 유지하고, 그 상태가
오늘 낼 것을 결정한다. 은행이 2만 문항이어도 학생이 오늘 마주하는 건 10~50문항이다.

## 1. 지금 구조의 세 가지 규모 문제

1. **무한 스트림 = 완료감 없음.** 출제가 안 푼 → 틀린 → 맞춘 순인데, 다 맞히면 맞춘
   문항을 무한 재순환한다(`bank_mode._pick` 마지막 폴백). "안 푼 9,800개"는 목표가
   아니라 절망이다.
2. **주간 챕터는 앞 200문항만 쓴다.** `chapters.py`가 전 과목 20주차 × 10문항 고정이라
   (`MAX_CHAPTERS * CHAPTER_SIZE = 200`), 초과 문항은 챕터 목차에 영영 안 나온다.
3. **출제 핫패스가 풀 전체를 스캔한다.** 문항 하나 낼 때마다 풀 전체 id를
   `LearningAttempt.content_id IN (...)`으로 대조한다(`_last_results`) — 만 개면 무겁다.

## 2. 학생×문항 상태 기계 (신규 테이블 `student_question_states`)

```
새 문항(행 없음) ──정답──> learning ──연속 2회 정답──> mastered
        ↑                     │                          │
        └────── 오답 시 강등 ←─┘        복습 만기(next_review_at)에만 재등장
```

| 필드 | 설명 |
|---|---|
| student_id / question_id (**UNIQUE 쌍**, 각 idx) | 소프트 참조(FK 없음 — collation 선례) |
| subject (idx) | 과목별 큐 조회용(문항의 과목을 복제 — 조인 회피) |
| state | `learning` \| `mastered`. **행이 없으면 = 안 푼(new)** — 테이블이 희소하게 유지되는 핵심(500문제 푼 학생 = 500행) |
| correct_streak / wrong_count / last_result | 상태 전이·통계 근거 |
| next_review_at (idx) | mastered의 복습 만기. SRS 사다리로 계산 |
| last_attempt_at | |

- **마스터 기준 = 연속 2회 정답.** 오답노트의 "2회 정답 = reviewed 승격"과 같은 리듬 —
  제품 전체가 "CatChap에서 '안다'는 두 번 맞힌 것"으로 통일된다.
- **SRS 사다리(고정)**: 정답 streak 1→+1일, 2→+3일, 3→+7일, 4→+14일, 5+→+30일.
  오답이면 streak=0·learning 강등·즉시 재출제 후보. (SM-2 같은 가변 알고리즘은
  과설계 — 고정 사다리가 설명 가능하고 실무에서 충분히 작동한다.)
- 갱신 시점: 은행 채점 경로(`captcha_api._credit_student`의 LearningAttempt 생성
  지점)에서 upsert. LearningAttempt는 그대로 남는다(기록 원장) — 상태는 파생 캐시다.
- **백필**: 기존 LearningAttempt에서 (학생, 문항)별 말미 연속 정답 수를 계산해 1회
  변환(스크립트, actor_band 백필 선례). 백필 전엔 전원 new로 동작해도 무해.

## 3. 출제 규칙 — "오늘의 큐"

우선순위: **① 복습 만기(mastered & next_review_at ≤ now) → ② 틀린 것(learning &
last_result=incorrect) → ③ 새 문항(행 없음)**. 셋 다 없으면 —

- **"오늘 완료" 상태를 반환한다**(다음 복습 예정일 포함). 무한 재순환 폐지.
- 학생이 원하면 **"복습 미리 하기"** — 만기 전 mastered 중 next_review_at이 가까운
  것부터 출제(상태 갱신은 동일). 강제 종료가 아니라 자연스러운 마침표 + 선택적 계속.
- 잠금 필터(강의 완주 `is_unlocked`)를 **먼저** 통과한 풀 안에서 분류한다(순서 불변).
- 비로그인(외부 임베드)은 상태가 없으므로 현행 유지(잠금 적용된 풀에서 랜덤).

**세트 단위**: 10문항 = 1세트. 프론트가 10문항마다 중간 결과(정답률·새 마스터 수·
오답노트 추가 수)와 "계속/그만"을 보여준다. 발급 경로는 현행 그대로(캡차 챌린지
문항 단위) — 세트는 프론트 카운터로 구현해 위젯·행동 데이터 경로를 건드리지 않는다.

## 4. 성능 — 왜 이게 스케일 답인가

- 출제 조회가 인덱스 3회(만기/틀린/새)로 끝난다. 풀 전체 IN 스캔 제거.
- "새 문항" 조회는 (잠금 통과 풀) − (그 학생의 상태 행 id들) — 학생 이력 크기에
  비례하지 풀 크기에 비례하지 않는다.
- 메모리 레지스트리(subject_banks)는 2만 문항 ≈ 수십 MB로 아직 감당 가능.
  10만+ 규모가 되면 DB 조회 + 캐시로 전환한다(알려진 한계로 기록).
- 진도 API(bank-progress)는 상태 테이블 COUNT로 대체(만기 수 추가 노출).

## 5. 구조 재편 (2단계) — 챕터의 미래

- 20주 달력 챕터(월요일 잠금)는 학교 시절 설계다. 성인 피벗과 맞지 않고 200문항
  한계가 있다. **재편: 과목 → 코스 문항 묶음 목차**(강의 화면의 코스 재구성과 동형).
- 잠금의 의미도 이관: 달력("월요일이 돼야") 대신 **강의 완주 잠금**("그 강의를 봐야")
  — 이미 구현돼 있다.
- **[결정 대기] 달력 잠금 폐지 여부** — 폐지를 제안하나 사용자 결정 필요.
- 함께: 새 문항 일일 상한(선택), LLM 대량 생성 대비 중복 감지(유사 문항 차단),
  운영자 표본 품질 검수, 문항별 정답률·노출수 지표(대시보드 연결).

## 6. 안 바꾸는 것 (정합)

| 축 | 영향 |
|---|---|
| 위젯·행동 데이터 경로 | 없음 — 출제 우선순위 계산만 교체, 발급/채점 경로 동일 |
| 강의 완주 잠금 | 없음 — 잠금 필터 먼저, 그 안에서 상태 분류 |
| 오답노트 | 없음 — 기존 기록·2회 승격 그대로(마스터 기준과 같은 리듬) |
| 오늘의퀴즈(습관 축) | 없음 — 별개 축 유지 |
| 수료 시험 | 없음 — 시험 응답은 은행 상태를 건드리지 않는다(`course-exam-design.md` §7) |

## 7. 공급 쪽 (만 개는 어디서 오나)

공급 엔진은 이미 있다: 강의 자막(STT) → LLM 생성 → 자기검증(봇 저항) → 강사 검수 →
은행 배치(`lecture-question-pipeline.md`). 규모에서 추가로 필요한 것은 중복 감지와
표본 검수뿐이며 2단계 항목이다.

## 8. 단계

**1단계 (엔진 교체 — 화면 최소 변경)**
1. `student_question_states` + 마이그레이션 `bank_srs_01`
2. 채점 경로 upsert + SRS 사다리
3. `bank_mode` 출제 우선순위 교체(만기→틀린→새) + "오늘 완료" 신호 + 복습 미리 하기
4. 진도 API에 만기 수 노출, 프론트 세트 카운터(10문항 결과)·완료 화면
5. 백필 스크립트(LearningAttempt → 상태) — 드라이런 → 실행
6. 테스트: 상태 전이(2회 마스터·오답 강등)·사다리 만기·완료 상태·잠금과의 합성·
   백필 멱등

**2단계 (구조 재편)**
- 코스 기반 목차(달력 잠금 폐지 — 결정 대기), 일일 신규 상한, 중복 감지,
  표본 검수, 문항 지표 → 대시보드.

## 9. 기본값 제안 (사용자 승인 대상)

- 마스터 기준: **연속 2회 정답** / SRS 사다리: **1·3·7·14·30일** / 세트: **10문항**
- 변경 시 이 문서와 구현 상수를 함께 고칠 것.
