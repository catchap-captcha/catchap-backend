# CatChap 온보딩·계정 연결 재설계 (제안)

> **진행 상황 (2026-07-06)**: 방향 확정 후 **일부 착수됨** — DB에 `student_join_codes`·`parent_invite_codes` 테이블 신설(마이그레이션 6), 기관 가입 운영자 승인(`/ops/registration-requests/*`)·기관 학생 생성/가입코드/비번초기화 API(`/orgs/{id}/students/*`) 구현, 학부모 초대코드 연결(`/parents/me/children/link-invite`) 추가. **남은 P0**: 학생 코드활성화 가입 화면 완성, 학부모 자동승인 완전 폐기. 아래 본문은 원래 설계안(참고).

- 상태: **제안 → 일부 구현** — 확정 후 구현 착수
- 작성 배경: 실서비스 준비도 보안 감사에서 발견된 **BLOCKER B1(학부모 무단 연결)**과, 그 과정에서 드러난 **학생 온보딩 설계 결함**을 함께 해결하기 위함
- 대상 서비스: **초등 저학년 중심**, 향후 고학년·학교 밖(에듀테크/개인)으로 **확장 가능성** 있음

---

## 1. 왜 바꾸는가 (문제 정의)

### 1.1 보안 결함 (감사에서 실제 재현됨)
- **B1 — 학부모 무단 연결**: 로그인한 학부모가 자녀 연결 화면에서 **임의의 학생 코드**(`CAT-1000~9999`, 9000개뿐)를 입력하면 **승인 없이 즉시** 그 아동에게 연결되어 개인정보(이름·나이·학급·학습 리포트)를 열람. 아동 대상 서비스에서 치명적.
- 근본 원인: ⑴ 연결이 자동 승인, ⑵ 학생 코드 공간이 작고 추측 가능, ⑶ 교사는 "누가 그 학생의 학부모인지" 알 방법이 없어 승인 판단 불가.

### 1.2 온보딩 설계 결함
- 현재 학생은 **이메일 인증으로 자가 회원가입**(`register_student`)하는데:
  - 저학년(7~8세)은 이메일이 없거나 스스로 인증 불가 — 비현실적
  - **아동 이메일 수집**은 미성년자 개인정보 이슈(법정대리인 동의 등)
  - 초기 합의("학생은 기관 발급 ID/PW, 이메일 가입은 관리자·교사·학부모만")와 **불일치**
- 학생 계정을 **학교가 발급하는 화면·기능이 없음**. 교사 "학생 추가"는 기존 학생을 반으로 이동만 시킬 뿐 생성 불가.

### 1.3 제약 (요구사항)
1. **학생 자가 가입 경험은 유지** — 아이가 "내가 가입했다"고 느끼게
2. **저학년 대응** — 아동 이메일 수집 없이
3. **확장 가능** — 고학년·학교 밖으로
4. **중복 방지·보안 견고**

## 2. 핵심 아이디어

> **가입 경험은 그대로 두고, "본인 확인" 역할만 이메일 → 학교 발급 코드로 교체한다.**

이메일이 하던 일은 "본인 확인" 하나뿐. 이것만 **학교가 발급하는 1회용 가입 코드**로 대체하고, 아이가 직접 하는 재미있는 부분(별명·비밀번호·아바타 선택)은 그대로 둔다. 학생은 여전히 스스로 가입하는 경험을 하되 이메일을 내지 않는다.

## 3. 확정 설계 결정 (+ 안전 조건)

세 결정 모두 **"안전하게 하려면" 조건을 반드시 포함**해야 구멍이 생기지 않는다.

### 결정 ① 학생 이메일 제거 + 학교 발급 가입 코드
- 아동 이메일 **수집하지 않음**.
- 공유 기관코드(`HS-EDU-2041`, 아무나 학생 생성 가능) 대신 **학생 1명당 1회용 가입 코드** 사용.
- **[안전 조건 — 가장 중요] 로그인 아이디와 아이가 고르는 것을 분리:**
  - **로그인 아이디 = 학교가 발급**(가입 코드에 내장, 전역 유일 보장) → 아이디 충돌 0, 크로스-학교 취약점 없음
  - **아이가 고르는 것 = 별명(nickname)·비밀번호·아바타** → 별명은 로그인 credential이 아니므로 **자유 중복 허용**(`별님` 수백 명 무방)
  - 이유: 학생이 아이디를 직접 고르게 하면 인기 아이디 충돌이 잦고, 기관별 유일로 완화하면 "다른 학교 같은 아이디+비번" 취약점이 되살아남. 둘 다 회피.

### 결정 ② 학생 비밀번호 재설정 = 교사 재설정
- 학생은 이메일이 없으므로 스스로 재설정 불가 → **담당 교사가 초기화**(학급 관리 화면).
- **[안전 조건]**
  - 재설정 시 **감사 로그 필수**(누가·언제·어느 학생)
  - 재설정 시 **해당 학생 refresh 토큰 폐기**(기존 세션 무효화)
  - (선택) 초기화 후 **첫 로그인 시 비밀번호 변경 강제**

### 결정 ③ 학부모 연결 = 학교 발급 초대 코드
- 학부모가 임의 학생 코드를 넣는 방식 폐기. 대신 **학교가 발급한 학생별 초대 코드**로만 연결.
- 신뢰의 근거는 "교사가 부모 신원을 확인"이 아니라 **"학교가 그 집에만 코드를 전달"**하는 전달 통로.
- **[안전 조건]**
  - **고엔트로피** 코드(예: `LINK-8F2K-9QX3`, 최소 8자 영숫자 = 수십억 조합) — 저엔트로피(`CAT-4823`류)면 무의미
  - **만료**(예: 7~30일) + **특정 학생 1명에만 귀속** + 입력 **rate limit**
  - **보호자 복수 허용**: 엄마+아빠 등 정당한 복수 연결을 막지 않도록 코드를 **N회(예: 2) 사용 허용** 또는 **교사 재발급** 가능. 이미 연결된 보호자의 재입력은 "이미 연결됨"으로 거절.
  - **교사 알림 + 연결 해제(revoke)**: 코드 유출(쪽지 분실 등) 대비, 연결 발생 시 교사에게 알림 및 해제 가능.

## 4. 전체 흐름

```
학교(교사/기관)        학생                          학부모
   │                  │                             │
   ├─ 반 생성          │                             │
   ├─ 학생 슬롯 등록     │                             │
   │  → 가입코드 발급 ──→ 코드 입력 → 별명·비밀번호·      │
   │    (아이디 내장)      아바타 직접 선택               │
   │                  │  (= 자가 가입 경험)             │
   │                  │  → 학생 계정 활성화 ✓           │
   │                  │                             │
   ├─ 학부모 초대코드 발급 ───────────────────────────→ 코드 입력
   │  → 가정에 전달                                   → 자녀 연결 요청
   │                                                → (교사 알림)
   │                                                → 연결 완료 ✓
   │
   └─ (필요 시) 학생 비밀번호 초기화 → refresh 폐기 + 감사 로그
```

### 4.1 학생 온보딩
1. 교사/기관이 학급을 만들고 학생 슬롯을 등록(개별 또는 명단 일괄) → 시스템이 **가입 코드**(로그인 아이디 내장) 생성.
2. 교사가 코드를 아이에게 전달(종이 쪽지/교실 화면).
3. 학생: 가입 화면에서 **가입 코드 입력** → **별명·비밀번호 설정 + 아바타 꾸미기** → 활성화.
4. 이메일·인증코드 단계 **없음**.

### 4.2 학부모 연결
1. 학생 등록 시 **학부모 초대 코드**가 함께 생성됨.
2. 교사가 그 아이 가정에 전달.
3. 학부모(이메일로 정상 가입) → 로그인 → **초대 코드 입력** → 연결.
4. 교사에게 연결 알림, 교사는 필요 시 해제 가능.

### 4.3 학생 비밀번호 찾기
- 학생 본인 재설정 없음. 교사가 학급 관리에서 초기화(§3-②의 안전 조건 적용).

## 6. 화면(디자인) 영향 — 확인 필요 항목

원본 handoff와 달라지는 부분(디자인 변경이므로 승인 대상):
1. **학생 회원가입에서 "이메일 + 인증코드" 단계 제거**
2. "기관코드" 입력 → **"가입 코드"** 입력으로 의미 변경(필드는 유지, 라벨·검증 변경)
3. 학생 가입 아이디 입력칸 제거(아이디는 코드 내장) — **별명 입력**으로 대체
4. 교사/기관 화면에 **"학생 등록 + 가입코드 발급"**, **"학부모 초대코드 발급"**, **"학생 비번 초기화"** 신규 추가
5. 학부모 자녀 연결: "학생 코드 아무거나 → 즉시 연결" → **"초대 코드 → 연결"**

## 7. 확장성 (향후)

가입 방식을 **기관별 설정값(모드)**로 두어 확장에 대응:
- **저학년(현재)**: 학교 발급 가입 코드 (기본)
- **고학년**: 동일 + 선택적 이메일(필수 아님, 비번 찾기용) 토글 추가 가능
- **학교 밖(에듀테크/개인)**: 별도 가입 모드 추가(예: 보호자 대행 생성 등)

기획서의 `auth_only / education_analysis` 모드 분리 사상과 일관.

## 9. 미결정 / 최종 확인 필요

1. **학생 이메일 완전 제거** 확정? (저학년 개인정보 보호 — 강력 권장)
2. 학생 비번 찾기 = **교사 재설정** 방식 확정?
3. 학부모 연결 = **초대 코드 방식** 확정?
4. 학생 로그인 아이디 = **학교 발급(전역 유일)**, 아이는 별명만 선택 — 확정? (충돌·취약 동시 해결의 핵심)
5. 초대 코드 **보호자 복수 허용 수**(기본 2명?) 및 **만료 기간**(7일? 30일?)
6. 기존 seed(이메일 가입 학생·자동 연결)는 개발용으로 유지 — 확정?

## 10. 현재 구현과의 차이 (구현 시 작업 범위)

- 제거: 학생 이메일 자가 가입(`register_student`의 email/email_code 경로), 학부모 자동 승인 연결
- 신규: 학생 슬롯 등록 + 가입코드 발급 API/화면, 가입코드 활성화 API/화면, 학부모 초대코드 발급/소비 API, 교사 비번 초기화, 교사 연결 알림/해제
- 변경: 학생 가입 UI(이메일 단계 제거, 아이디→별명), 학부모 연결 UI(초대코드), 로그인 아이디 발급 규칙
- 유지: 학생 로그인 아이디 전역 유일(UNIQUE), 코드 hash 저장, RBAC, rate limit 인프라(§보안 수정과 공유)

> 본 재설계는 보안 감사 BLOCKER B1을 해소하며, 함께 처리하면 좋은 인접 항목: B2(rate limit — 코드 입력에 공유), B3(탈퇴 학생 로그인 차단), 학부모 연결 감사 로그.
